# Telegram-бот к языковой модели

Бот шлёт текст сообщения в языковую модель и возвращает ответ в чат.
Работает **без памяти**: каждый запрос — `system prompt + текущее сообщение`,
история не хранится и модели не передаётся.

Два сменных бэкенда, переключение только переменной `LLM_PROVIDER`, код не трогается:
`ollama` (локально, OpenAI-совместимый `/v1`, по умолчанию `qwen3:1.7b`) и
`anthropic` (родной SDK, `claude-opus-5`).

Спецификация — [SPEC-tg-bot.md](SPEC-tg-bot.md), замеры токенов — [REPORT.md](REPORT.md).

## Установка

```bash
# если нет uv:
curl -LsSf https://astral.sh/uv/install.sh | sh

uv venv .venv
uv pip install --python .venv/bin/python -r requirements.txt
```

Вместо uv подойдёт штатный venv, если в системе есть пакет `python3-venv`:

```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
```

## Настройка

```bash
cp .env.example .env
```

Заполнить `TELEGRAM_BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
В `.env.example` два профиля: локальная Ollama (активен) и Anthropic
(закомментирован, нужен `ANTHROPIC_API_KEY`). Остальные переменные
(`LLM_MODEL`, `LLM_TIMEOUT_SECONDS=180`, `LLM_MAX_TOKENS`, `SYSTEM_PROMPT`)
описаны там же и имеют рабочие значения по умолчанию.

## Запуск

```bash
ollama serve && ollama run qwen3:1.7b   # только для профиля ollama
.venv/bin/python bot.py
```

Транспорт — long polling, публичный IP не нужен. Первый запрос после старта
Ollama долгий: модель грузится в память, отсюда таймаут 180 секунд.

## Проверка

```bash
.venv/bin/python -m pytest      # 20 тестов, сеть не используется
```

Живая проверка: `/start` в чате с ботом — в приветствии видно активную модель;
любое текстовое сообщение должно вернуть ответ. Затем сменить `LLM_PROVIDER`
на `anthropic` в `.env`, перезапустить бота и повторить — ответ приходит уже
из облака, код при этом не менялся.

Если модель недоступна, бот не падает, а отвечает подсказкой, что проверить
(запущена ли Ollama, верен ли `LLM_BASE_URL`).

## Структура

```
bot.py            хендлеры, нарезка ответа под лимит 4096, polling
config.py         чтение и валидация переменных окружения
llms/__init__.py  call_llm(prompt) -> str: выбор провайдера, вырезание <think>
llms/ollama.py    локальная модель через AsyncOpenAI
llms/anthropic.py облачная модель через AsyncAnthropic
llms/errors.py    LLMError / LLMTimeoutError
tests/            pytest, оба клиента замоканы
```

`bot.py` знает только про `call_llm`. Третий провайдер = новый файл в `llms/`
и одна запись в `_GENERATORS`.

## Решения по неоднозначностям ТЗ

- `llms/errors.py` — файл сверх списка модулей: общие ошибки нужны и провайдерам,
  и `llms/__init__.py`, иначе круговой импорт. Наружу доступны как `from llms import LLMError`.
- Клиент создаётся на запрос и закрывается в `finally` — бот малонагруженный,
  переиспользуемый клиент пришлось бы инвалидировать при смене конфигурации.
- Статус «печатает» показывается один раз, без фоновой задачи на переотправку:
  при долгом ответе он погаснет.
- `call_llm(prompt, config=None)` — второй параметр только для тестов,
  `bot.py` вызывает строго `call_llm(prompt)`.
- Вырезание `<think>` — в `llms/__init__.py`, общее для всех бэкендов;
  если после вырезания пусто, уходит исходный текст.
- Нарезка длинного ответа: перенос строки → пробел → жёсткий разрез по 4096.
- Ошибка конфигурации при старте — сообщение в лог и код возврата 1, не traceback;
  токены в логе маскируются.

Памяти диалога нет по требованию задания.
