# Отчёт: аудит токенов агента (задание 6)

Состояние: **инфраструктура готова, замер «до» ещё не снят.** Разделы с цифрами
заполняются после прогонов.

## Решения по неоднозначностям ТЗ

1. **Модель и effort — параметры замера, temperature не используется.**
   `bench.run --model` (по умолчанию `claude-sonnet-5`; первая серия замеров
   шла на `claude-haiku-4-5`, см. раздел «Замеры на claude-haiku-4-5») и `--effort`
   (уходит как `output_config={"effort": ...}`); оба пишутся в метаданные
   замера. **Факт:** на пробном прогоне `claude-haiku-4-5` ответила 400
   `This model does not support the effort parameter`
   (request_id `req_011CehtzRKZbndUtxS6jnHUS`), поэтому по умолчанию `effort`
   не отправляется и замер идёт без него; флаг оставлен для моделей, где
   параметр есть. В Anthropic API 1.0 параметры сэмплинга
   (`temperature`, `top_p`, `top_k`) удалены, а не перенесены: SDK 1.0.0 не
   принимает их даже как аргумент. Современная замена — `effort`: меньше
   размышлений, стабильнее и дешевле. Отсутствие детерминизма компенсируется
   пятью прогонами на задачу и разбросом success rate по прогонам в сводке.
   В `Config` добавлены `llm_temperature` (отправляется только в Ollama, где
   параметр поддерживается) и `llm_effort` (только Anthropic); оба по
   умолчанию `None`, бот в Telegram работает как раньше.
2. **Usage у Ollama.** Проект ходит в Ollama через OpenAI-совместимый `/v1`,
   где счётчики называются `prompt_tokens` / `completion_tokens`. Парсер читает
   сначала нативные `prompt_eval_count` / `eval_count`, затем OpenAI-имена;
   кэша нет — `cached_input_tokens = 0`.
3. **Пятое поле в `Usage`: `cache_write_input_tokens`.** Запись в кэш Anthropic
   тарифицируется ×1.25 к обычному вводу. Без этого поля стоимость замера
   «после» (с prompt caching) была бы занижена, а экономия — завышена.
3a. **`Usage.reasoning_tokens`.** Anthropic отдаёт токены размышления в
   `usage.output_tokens_details.thinking_tokens`; они уже входят в
   `output_tokens` и оплачиваются по тарифу output, поэтому в стоимость
   отдельно не входят, а показываются в сводке как «из них reasoning».
   На модели без расширенного мышления поле 0. Ollama через
   OpenAI-совместимый `/v1` может отдать
   `completion_tokens_details.reasoning_tokens` — читается оттуда.
4. **Пометка «провайдер не отдал usage»** — поле `usage_missing` в событии,
   вычисляется как «оба счётчика нулевые» (`Usage.is_reported`).
5. **`run_id` и `step` передаются через `contextvars`**
   (`observability/run_context.py`), а не через сигнатуры `call_llm_step` и
   `run_tool`: харнесс меняется на две строки, сигнатуры и существующие тесты не
   трогаются. Вне цикла агента (`call_llm`) телеметрия не пишется.
6. **Прайс — в `bench/pricing.py`** (таблица по моделям, USD за 1M токенов,
   раздельно input / output / cached read / cache write). Локальная и
   неизвестная модель стоят 0.
7. **Рост контекста считается точно, без оценок по символам.**
   - system prompt (со скиллами) и описания инструментов — константы: их размер
     считается один раз на замер через `messages.count_tokens` и лежит в meta
     (`system_prompt_tokens`, `tool_descriptions_tokens`); рост 0.
     Постановка задачи — остаток `input(1) − system − tools`.
   - прирост истории на витке N = `input(N) − input(N−1)` (все входные токены,
     включая кэшированные) — точное число от API;
   - повторно отправленные токены на витке N = `input(N−1)` целиком: payload
     витка N полностью содержит payload витка N−1 (харнесс только дописывает);
   - прирост раскладывается на «ответ модели» и «вывод инструментов» по
     соотношению, которое даёт `count_tokens` на самих добавленных блоках во
     время прогона (два вызова на виток: пара «ответ + пустые результаты» и
     пара «ответ + реальные результаты»; их разность — вывод инструментов).
     Если `count_tokens` недоступен (Ollama, сбой сети), доли берутся по
     символам только внутри прироста; метод каждого витка пишется в событие,
     сводка показывает, сколько витков посчитано каким способом.
   В событие также пишутся размер в символах и хеш каждого блока payload;
   содержимое команд и выводов в JSONL не попадает.
   **Наблюдение:** описания инструментов весят 1 726 токенов при 589 символах
   спецификации. Разность «с tools / без tools» включает служебную преамбулу
   провайдера для tool use — это реальная цена включения инструментов, а не
   размер нашей спецификации.
8. **Задача 8 (`ls /nonexistent`).** Абсолютный путь вне рабочего каталога
   отклоняется проверкой путей ещё до запуска, то есть это был бы тот же отказ,
   что в задаче 9. Чтобы команда действительно выполнилась и упала, задача
   просит `ls nonexistent/` относительно рабочего каталога.
9. **Задача 9 (вне allowlist)** — `uname -a`: безобидная команда, которой нет в
   белом списке.
10. **Задача 12** — GET к `https://api.github.com/repos/python/cpython`,
    проверка вхождения `python/cpython` (стабильное поле `full_name`).
11. **Проверка «точное число»** — число как отдельный токен в тексте
    (не часть другого числа), потому что финальный ответ обычно содержит слова.
12. **Файлы замера.** Агрегат `bench/results/<label>.json` (метаданные,
    сводка, timeline одного запуска) коммитится. Сырьё остаётся локально в
    `telemetry/` под `.gitignore`: `<label>.events.jsonl` (телеметрия) и
    `<label>.outcomes.jsonl` (вердикты с обрезанным до 300 символов ответом
    агента). Отчёт и дашборд строятся только из агрегата. Повторный запуск
    с той же меткой отклоняется без `--force` — защита от правки замера «до»
    задним числом. Телеметрия бота вне бенчмарка пишется в
    `telemetry/events.jsonl`, путь переопределяется переменной `TELEMETRY_PATH`.

13. **Проверка задачи 10 правилась один раз.** Исходная проверка требовала,
    чтобы в ответе не упоминалось имя проигравшего файла, и отклонила верный
    ответ «sample.py (35 строк против 13 у notes.txt)» — ложноотрицательное
    срабатывание, дефект измерения, а не строгость. Оставлено только
    требование назвать победителя. После правки все замеры на
    `claude-sonnet-5` (`before`, `after-cache`, `after-exec`) пересняты заново;
    результаты, снятые до правки, недействительны и в отчёте не используются.
    Замеры на Haiku (`before-haiku`, `after-cache-haiku`) правкой не
    затронуты: там задача 10 проходила всегда.

## Оптимизации и замеры «после»

Каждая оптимизация мерится от базы `before`, не по цепочке: метки
`after-cache`, `after-skills`, `after-tools`, финальный `after-all`.

### 1. Prompt caching константного префикса

`cache_control: ephemeral` на system-блоке и на последнем описании
инструмента. Скиллы внутри system-блока.

#### На claude-haiku-4-5 (`before-haiku` → `after-cache-haiku`, 5 прогонов)

| метрика | before-haiku | after-cache-haiku | изменение |
|---|---|---|---|
| стоимость | $0.4622 | $0.4704 | +1.8% |
| input tokens | 428 293 | 435 313 | +1.6% |
| cached input / cache write | 0 / 0 | 0 / 0 | — |
| cache hit rate | 0% | 0% | — |
| success rate (локальные) | 96% (90…100%) | 100% (100…100%) | +4 п.п. |
| success rate (сетевые) | 100% | 100% | — |

**Эффекта нет, кэш не создаётся.** Причина проверена по документации и
двумя пробами, не по памяти:

- Документация Anthropic, раздел «Cache limitations» страницы
  <https://platform.claude.com/docs/en/build-with-claude/prompt-caching>,
  таблица «minimum cacheable prompt length»: Claude Haiku 4.5 — 4 096 токенов,
  Claude Sonnet 5 — 1 024 токена. Префикс короче минимума не кэшируется даже
  с `cache_control`, ошибки при этом нет.
- Наш константный префикс на `claude-haiku-4-5`: описания инструментов 1 726
  + system 1 436 = 3 162 токена, меньше 4 096.
- Проба на `claude-haiku-4-5`: два одинаковых запроса подряд с теми же метками —
  `cache_creation_input_tokens = 0`, `cache_read_input_tokens = 0` в обоих.
- Проба на `claude-sonnet-5` с тем же префиксом: первый вызов
  `cache_creation_input_tokens = 2064`, `cache_read_input_tokens = 0`; второй —
  `cache_creation_input_tokens = 0`, `cache_read_input_tokens = 2064`.
  Кэш создаётся и читается. Тот же префикс у Sonnet 5 занимает 2 064 токена
  против 3 162 у Haiku 4.5: токенайзеры разные.

Разница в стоимости +1.8% — шум модели (другие ответы, чуть больше витков),
не эффект изменения. Оптимизация оставлена в коде как есть.

#### На claude-sonnet-5 (`before` → `after-cache`, 10 прогонов)

| метрика | before | after-cache | изменение |
|---|---|---|---|
| стоимость | $1.2667 | $0.3673 | -71.0% |
| стоимость input (без кэша) | $1.1253 | $0.1245 | -88.9% |
| стоимость cached input | $0 | $0.0987 | — |
| стоимость cache write | $0 | $0.0052 | — |
| стоимость output | $0.1414 | $0.1389 | -1.7% |
| input tokens без кэша | 562 674 | 62 267 | -88.9% |
| cached input tokens | 0 | 493 296 | — |
| cache write tokens | 0 | 2 064 | — |
| cache hit rate | 0% | 88.5% | — |
| success rate (локальные) | 100% (100…100%) | 100% (100…100%) | 0 п.п. |
| success rate (сетевые) | 100% | 100% | — |

**Эффект: -71% стоимости при неизменном success rate.** Кэшируется только
константный префикс (описания инструментов + system со скиллами, 2 064
токена у Sonnet 5): запись в кэш за весь замер произошла один раз — 5-минутный
кэш переживал переходы между задачами, все 240 последующих вызовов читали
его. История витков после breakpoint не кэшируется, поэтому «повторно
отправленные токены» не изменились (260 810, 47%): они по-прежнему
отправляются, но константная их часть теперь стоит ×0.1.

Три факта к результату:

1. **Запись в кэш произошла один раз за 240 вызовов**: задачи шли подряд, и
   пятиминутный TTL не истекал. В живом боте с редкими сообщениями кэш будет
   истекать, и каждый первый вызов после паузы заплатит за запись ×1.25.
   Поэтому −70% — верхняя оценка для плотного потока, а не типичное значение.
2. **Разложение остатка после кэширования** ($0.3673): выход 38%,
   некэшируемая история (input без кэша) 34%, чтение кэша 27%, запись 1%.
   До оптимизации на константный префикс (2 064 tok × 240 вызовов =
   495 360 tok, 88% входных токенов) приходилось 78% полной стоимости
   и 88% стоимости входа.
3. **Описания инструментов у Sonnet 5 весят 595 токенов против 1 726 у
   Haiku 4.5** при одной и той же спецификации в 589 символов: служебная
   преамбула провайдера для tool use модельно-зависима.

**Разрешение метрики success rate.** Правка не могла повлиять на поведение
модели: кэш не сработал, на вход ушли те же токены. Тем не менее success rate
локальных задач изменился с 96% (разброс по прогонам 90…100%) до 100%
(100…100%). Значит, шум метрики при 10 задачах × 5 прогонов не меньше
4 п.п. — хуже, чем порог «падение не более 2 п.п.» из ТЗ. Это надо
предъявить рядом с итоговым сравнением: разницу success rate в пределах
±4 п.п. между замерами нельзя приписывать оптимизации.
