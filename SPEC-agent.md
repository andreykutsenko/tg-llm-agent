# ТЗ: минимальный AI-агент поверх Telegram-бота

Домашнее задание №4 курса «Тренинг для Fullstack-программистов» (coders.su),
выдано на звонке 5 «Agents and Yolo», 2026-08-24.

Надстройка над заданием №2 (тег `v1-bot` в этом же репозитории).
Этот файл — единственный промпт, которым выполняется задание.

---

````text
<objective>
Превратить существующего Telegram-бота в минимального автономного агента:
добавить агентный цикл (харнесс), инструмент выполнения консольных команд
и файлы-скиллы с инструкциями. Учебная задача: цель — понять устройство
цикла «модель просит действие → код выполняет → результат возвращается модели»,
а не собрать максимум возможностей.
</objective>

<constraints>
Реализуй полностью, без уточняющих вопросов.
Неоднозначность — выбери вариант, запиши в README, продолжай.
Не используй псевдокод: весь код должен запускаться.
В конце прогони pytest и покажи вывод.
</constraints>

<process>
Работать в ветке feat/agent-harness, ветку создать от main.
main не трогать: состояние задания №2 зафиксировано тегом v1-bot и должно
остаться воспроизводимым.
Ничего не коммитить и не пушить без отдельной команды.
</process>

<baseline>
Существующий код: bot.py, config.py, llms/ (ollama.py, anthropic.py, errors.py),
tests/. Читать его перед изменениями и сохранять принятые там решения:
конфигурация из переменных окружения, секреты только в .env, маскирование
в логах, нарезка ответа под лимит Telegram 4096.
</baseline>

<stack>
Python 3.11+. К существующим зависимостям (aiogram, openai, anthropic,
python-dotenv) НИЧЕГО не добавлять. Тесты: pytest, pytest-asyncio.
</stack>

<commands>
Установка:  uv pip install --python .venv/bin/python -r requirements.txt
Тесты:      .venv/bin/python -m pytest -q
Запуск:     .venv/bin/python bot.py
</commands>

<architecture>
Новое:
  harness.py         агентный цикл: вызов модели → разбор запроса на инструмент →
                     выполнение → возврат результата модели → повтор до финального ответа
  tools/__init__.py  реестр инструментов: описание для модели + функция-исполнитель
  tools/exec.py      выполнение консольных команд с проверками
  skills/*.md        текстовые инструкции, подкладываются модели в системный промпт

Изменяется:
  llms/              контракт расширяется: см. <llm_contract>
  bot.py             вместо прямого call_llm вызывает харнесс
</architecture>

<llm_contract>
Сейчас call_llm(prompt) возвращает строку. Для цикла этого мало: модель должна
уметь вернуть запрос на вызов инструмента.

Ввести общий для провайдеров результат: либо финальный текст, либо список
вызовов инструментов (имя + аргументы). Форматы у провайдеров разные —
OpenAI-совместимый tools/tool_calls у Ollama и native tool use у Anthropic;
приводить оба к одному виду внутри llms/, наружу отдавать одинаково.

bot.py и harness.py не должны знать, какой провайдер активен.

**Провайдер по умолчанию в агентном режиме — anthropic.** Причина: цикл требует
точного попадания в формат вызова инструментов, модели уровня qwen3:1.7b
там ненадёжны. Локальный профиль оставить рабочим — он не должен ломаться,
но дефолтом в .env.example для агентного режима идёт anthropic.

Задание №2 это не затрагивает: его состояние зафиксировано тегом v1-bot,
там локальный профиль остаётся по умолчанию.

Если на локальной модели цикл ведёт себя хуже — зафиксировать наблюдение
в README (в чём именно проявляется), а не обходить костылями в харнессе.
</llm_contract>

<harness>
Цикл: отправить модели системный промпт + скиллы + сообщение пользователя
+ описания инструментов. Далее пока модель просит вызовы:
выполнить, добавить результат в контекст шага, отправить снова.
Выход из цикла — финальный текстовый ответ.

Ограничение шагов: переменная AGENT_MAX_STEPS, по умолчанию 8, допустимый
диапазон 5–10. Достигнут предел — вернуть пользователю то, что есть,
с явной пометкой, что лимит шагов исчерпан. Молча обрываться нельзя.

Контекст цикла живёт ровно один запрос пользователя и после ответа
отбрасывается. Память между сообщениями по-прежнему НЕ ведётся —
требование задания №2 остаётся в силе.

Каждый шаг логировать: номер, имя инструмента, аргументы, длину результата.
Это единственный способ понять, почему агент пришёл к ответу.
</harness>

<tool_exec>
Инструмент exec выполняет консольную команду и возвращает stdout, stderr
и код возврата.

Проверки обязательны, порядок важен:
1. Команда запускается БЕЗ шелла (список аргументов, не строка) — исключает
   подстановку через ;, &&, |, кавычки и обратные апострофы.
2. Разрешён только список команд из EXEC_ALLOWLIST (по умолчанию:
   curl, cat, ls, date, head, tail, wc, grep). Всё остальное отклоняется
   с понятным для модели объяснением, что именно запрещено.
3. Таймаут EXEC_TIMEOUT_SECONDS, по умолчанию 20. Превышение — снять процесс.
4. Рабочий каталог ограничен EXEC_WORKDIR, по умолчанию каталог проекта.
4a. Подпроцесс запускается с ОЧИЩЕННЫМ окружением: наследовать переменные
   процесса бота нельзя. Передавать только явный минимум (PATH, LANG).
   Причина: в окружении бота лежат TELEGRAM_BOT_TOKEN и ANTHROPIC_API_KEY,
   и без очистки любая разрешённая команда получает к ним доступ.
5. Вывод обрезать до EXEC_MAX_OUTPUT символов, по умолчанию 4000,
   с явной пометкой об обрезке — иначе один ls забьёт контекст.

Отказ — это нормальный ответ инструмента модели, а не исключение:
модель должна получить текст, понять причину и попробовать иначе.

ВАЖНО про границы этой защиты. Allowlist сужает поверхность, но песочницей
НЕ является: он ограничивает имена команд, а не их аргументы. Пара cat + curl
позволяет прочитать доступный файл и отправить его наружу. Попасть туда модель
может не по злому умыслу, а по prompt injection — через текст, присланный
в чат. Поэтому обязательны очистка окружения (пункт 4a), ограничение каталога
и список разрешённых отправителей. В README честно написать, что настоящие
границы — это отдельный пользователь ОС или контейнер, а не allowlist.
</tool_exec>

<access_control>
Бот отвечает только отправителям из TELEGRAM_ALLOWED_IDS (список числовых id
через запятую). Сообщения от остальных игнорировать, факт логировать.
Список пуст — бот отвечает всем и пишет предупреждение при старте:
для агента с exec это небезопасно.
</access_control>

<skills>
Каталог skills/, файлы .md, все загружаются при старте и подкладываются
в системный промпт.

Создать два примера:
- skills/weather.md — тип Б, рутина: получить погоду через
  https://wttr.in/Minsk?0 и сформировать сводку для пользователя.
  Скиллы не вызываются как инструменты: они загружаются в системный промпт
  при старте и читаются моделью. Действие выполняет exec, скилл лишь
  объясняет, что именно им делать.
- skills/http-api.md — тип А, инструкция к инструменту: как обращаться
  к HTTP API через curl, как читать код ответа, что делать при ошибке.

Ограничение по размеру: суммарно все скиллы не длиннее SKILLS_MAX_CHARS,
по умолчанию 8000. Превышение — понятная ошибка при старте со списком файлов
и их размеров. Причина: скиллы уходят в КАЖДЫЙ запрос, а незаметно обрезанная
инструкция хуже отсутствующей.
</skills>

<boundaries>
Всегда: ограничивать число шагов цикла; проверять команду по allowlist;
        логировать каждый шаг и каждый вызов exec.
Сначала спроси: добавлять зависимости; расширять allowlist; менять
        транспорт Telegram; выносить агента за пределы рабочего каталога.
Никогда: выполнять команду через шелл-строку; передавать подпроцессу
        окружение бота; читать .env через exec; отключать лимит шагов;
        добавлять память между сообщениями пользователя; коммитить .env;
        утверждать в документации, что allowlist делает exec безопасным.
</boundaries>

<error_handling>
Ошибка инструмента — текстовый результат модели, цикл продолжается.
Ошибка модели или сети — понятный ответ пользователю, процесс не падает.
Ошибка конфигурации при старте — сообщение и код возврата 1, без traceback.
Stack trace пользователю не показывать никогда.
</error_handling>

<tests>
pytest, сеть и подпроцессы мокать.
1. Цикл завершается, когда модель вернула финальный текст.
2. Цикл обрывается на AGENT_MAX_STEPS и сообщает об этом пользователю.
3. Результат вызова инструмента попадает в следующий запрос к модели.
4. Оба провайдера приводятся к общему виду результата — проверить на моках обоих.
5. exec отклоняет команду вне allowlist.
6. exec не выполняет подстановку: аргумент вида "; rm -rf /" остаётся
   обычной строкой и командой не становится.
7. Таймаут exec снимает процесс и возвращает понятный текст.
7a. Подпроцесс не видит переменных окружения бота: команда, печатающая
    окружение, не содержит ни TELEGRAM_BOT_TOKEN, ни ANTHROPIC_API_KEY.
7b. Попытка прочитать .env через exec отклоняется.
8. Вывод длиннее лимита обрезается с пометкой.
9. Сообщение от id вне TELEGRAM_ALLOWED_IDS остаётся без ответа.
10. Скиллы из skills/ попадают в системный промпт.
11. Суммарный размер скиллов сверх лимита даёт ошибку при старте.
12. Память между сообщениями не накапливается: два подряд запроса
    не видят контекста друг друга.
</tests>

<done_when>
- pytest зелёный, сеть и подпроцессы не используются
- бот в Telegram выполняет скилл weather.md: запрашивает погоду через exec
  и возвращает сводку
- в логе видны шаги цикла с именами инструментов
- команда вне allowlist отклоняется, в чат приходит осмысленный ответ
- .env.example дополнен новыми переменными; в агентном режиме профиль
  anthropic активен по умолчанию, локальный остаётся закомментированным
- проверено на обоих провайдерах: как ведёт себя цикл на каждом,
  различия описаны в README
- README дополнен разделом про агентный режим: как включить, какие переменные,
  как добавить свой скилл, чем ограничен exec
- в README раздел с принятыми решениями по неоднозначностям ТЗ
</done_when>
````
