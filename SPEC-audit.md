Работа ведётся в репозитории `tg-llm-agent`, поверх состояния тега `v2-agent`.

<architecture>
Существующий код трогаем минимально. Точки врезки:

1. llms/protocol.py — в LLMResult добавить поле usage: Usage.
   @dataclass(frozen=True) class Usage:
       input_tokens, output_tokens, cached_input_tokens, latency_ms
   Отсутствие данных у провайдера = нули, а не None.

2. llms/anthropic.py — parse_response читает response.usage:
   input_tokens, output_tokens, cache_read_input_tokens.
   llms/ollama.py — prompt_eval_count / eval_count, кэша нет → 0.

3. observability/recorder.py — НОВЫЙ модуль. Пишет JSONL, по строке на событие.
   Не агрегирует, не считает статистику: только запись сырья.
   record_llm_call(run_id, step, model, usage, cost)
   record_tool_call(run_id, step, tool_name, input_size, output_size, duration_ms)

4. llms/__init__.py, call_llm_step — обёртка: замерить время, получить LLMResult,
   вызвать record_llm_call. Единственная точка вызова модели.

5. tools/__init__.py, run_tool — то же самое для инструментов.

6. harness.py, run_agent — завести run_id (uuid4) и прокинуть в записи.
   Больше в харнессе не менять ничего.

7. bench/ — НОВЫЙ пакет: tasks.py (набор задач), run.py (прогон), report.py
   (агрегация, дашборд, сравнение). Логика отделена от CLI: функции принимают
   аргументы и возвращают данные, argparse и печать — тонкий слой сверху.

Стоимость считается из прайса в config (BLL_PRICE_* или таблица в bench/pricing.py),
раздельно по input / output / cached. Цифры прайса — в одном месте, не по коду.
</architecture>

<benchmark>
Набор фиксирован ДО первого замера и дальше не меняется. Меняешь набор —
обесцениваешь сравнение.

12 задач, из них 10 локальных (детерминированные) и 2 сетевых (помечены flaky).
Фикстуры лежат в bench/fixtures/ и коммитятся.

Локальные:
 1. арифметика через exec → в ответе есть "4"
 2. число строк в bench/fixtures/sample.py → точное число
 3. номер строки с заданным словом в фикстуре → точное число
 4. перечислить файлы в bench/fixtures/ → все три имени в ответе
 5. текущая дата → соответствует ^\d{4}-\d{2}-\d{2}$
 6. сумма чисел в bench/fixtures/numbers.csv → точное число
 7. самый большой файл в фикстурах → его имя
 8. заведомо падающая команда (ls /nonexistent) → агент объясняет ошибку,
    не выдумывает содержимое каталога
 9. команда вне allowlist → агент передаёт отказ инструмента человеческим текстом
10. двухшаговая: сравнить число строк в двух файлах → имя большего

Сетевые (считаются отдельно, в основную метрику success rate не входят):
11. погода в заданном городе через скилл weather

Критерий успеха одной задачи — ВСЕ три условия:
  - финальный текст удовлетворяет проверке задачи (regex или точное вхождение);
  - прогон не завершился исключением;
  - limit_reached == False.

Прогонов: 3 на каждую задачу, оба замера. temperature=0, модель зафиксирована
в конфиге замера и записана в отчёт.

<audit>
Аудит обязан отвечать на четыре вопроса:
1. какой инструмент даёт больше всего токенов;
2. какой виток самый дорогой;
3. какой тип контекста растёт быстрее: system prompt / история / вывод инструментов;
4. сколько входных токенов отправлено ПОВТОРНО.

Четвёртый считать так: на каждом витке входной payload раскладывается на блоки
(system, каждое сообщение истории). Токены блока, который уже отправлялся на
предыдущем витке этого же run_id, считаются повторными. Отчёт даёт абсолютное
число и долю.

Известно заранее, проверить в замере:
- build_system_prompt кладёт ВСЕ скиллы в system на каждом шаге;
- в запросе к Anthropic нет cache_control, то есть cached_input_tokens = 0.
</audit>

<dashboard>
Один статический HTML, генерируется из JSONL, открывается локально.
Обязательно:
- сводка: задач, суммарно токенов по типам, стоимость, среднее на задачу,

- TIMELINE ОДНОГО ЗАПУСКА по виткам: для каждого витка — input/output токены
  и накопленный контекст. Это ключевая картинка задания.
</dashboard>

<optimizations>
Ровно три, каждая измеряется ОТДЕЛЬНЫМ прогоном, чтобы был виден вклад каждой.

1. Prompt caching: пометить system-блок cache_control (ephemeral). Скиллы и
   описания инструментов не меняются между витками — это идеальный кандидат.
2. Token-aware вывод exec: вместо первых N символов возвращать голову и хвост
   с пометкой о пропущенном объёме; для многострочного вывода — лимит строк.
3. Компакция истории: начиная с заданного витка старые пары
   «вызов инструмента → результат» заменяются краткой сводкой.

Каждая — отдельным коммитом. Если какая-то не даёт эффекта, это результат:
записать в отчёт и оставить, а не прятать.
</optimizations>

<error_handling>
Сбой записи телеметрии НЕ должен ронять агента: пишем предупреждение в лог
и продолжаем. Наблюдение не важнее работы.
Провайдер не отдал usage — нули и пометка в записи, а не исключение.
Упавшая задача бенчмарка попадает в отчёт как failed с текстом ошибки,
прогон остальных не прерывается.
</error_handling>

<boundaries>
Всегда: сначала замер «до», потом оптимизации; каждая оптимизация — отдельный
        коммит и отдельный замер; бенчмарк неизменен между замерами.
Сначала спроси: добавлять зависимости; менять набор задач бенчмарка;
        менять поведение агента способом, влияющим на ответы пользователю.
Никогда: подгонять бенчмарк под результат; править замер «до» задним числом;
        коммитить .env, ключи и сырые JSONL с содержимым команд.
</boundaries>

<tests>
Внешних вызовов в тестах нет: провайдер и инструменты мокаются.
1. Usage корректно извлекается из ответа Anthropic (в т.ч. cache_read).
2. Usage у Ollama маппится из prompt_eval_count / eval_count.
3. Провайдер не вернул usage → нули, исключения нет.
4. record_llm_call пишет ровно одну валидную JSON-строку на вызов.
5. Падение записи телеметрии не роняет run_agent.
6. Счётчик повторных токенов на синтетическом прогоне из трёх витков
   даёт заранее известное число.
7. Проверка задачи бенчмарка: правильный ответ → success, неправильный → fail.
8. limit_reached == True делает задачу failed, даже если текст похож на верный.
9. Агрегация стоимости раздельно по input / output / cached.
10. report сравнивает два замера и считает дельту в процентах.
</tests>
